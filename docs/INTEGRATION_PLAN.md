# 平台融合与实测计划

## 采集项目的职责边界

| 项目 | 采用方式 | 不做的事 |
|---|---|---|
| MediaCrawler | 独立运行，作为第一批国内平台采集来源；导出 JSONL/CSV 后由本项目导入 | 不复制上游源码；不假设所有平台字段一致 |
| CreatorHub | 独立运行，作为监控工作台/本地服务参考 | 不把整套桌面工作台并入本项目 |
| media-crawler-easy | 借鉴环境检测、执行状态机、空数据回退、报告校验 | 不把 Agent Skill 当成采集引擎 |
| wechat_spider | 公众号专项实验连接器候选 | 未验证微信版本、登录环境前不宣称可用 |
| BilibiliCrawler | B站专项采集/分析备选 | 先与 MediaCrawler 的 B站采集对比，避免重复 |
| YouTube Data API | 海外平台官方 API 候选 | 需单独配置 API Key 与配额 |

## 平台路线

### 第一批：MediaCrawler 导入验证
- 小红书、抖音、快手、微博、B站、贴吧、知乎。
- 验证每个平台导出的评论字段、评论时间字段、楼中楼结构、分页完整性。
- 不以 README 的平台勾选表代替真实测试。

### 第二批：专项连接器
- 今日头条：先确认公开内容及评论可见范围、稳定字段和访问条件，再决定实现。
- 公众号：评估 wechat_spider 的本地微信依赖、评论可见性和数据导出。公众号评论不是所有文章都可见。
- B站：如果上游字段不全，再评估 BilibiliCrawler。

### 第三批：需求识别
- 规则识别作为可解释基线。
- LLM 输出结构化标签、需求描述、场景、证据引用和置信度。
- 每个需求必须关联原始评论 ID；不得只保留模型摘要。
- 聚类按需求相似度合并，保留每条独立评论证据。

## 72 小时规则
- 使用评论自身发布时间，不使用帖子发布时间替代。
- 保存原帖发布时间供内容新鲜度分析。
- 缺失或无时区的时间不进入“最近 72 小时”结果。
- 采集时间与发布时间分开记录。
- 以平台评论 ID 去重；缺少 ID 时使用带内容 ID 和行号的稳定回退键，并标记来源数据。

## 实测验收清单
每个平台至少测试 5 篇内容：
1. 搜索发现或指定链接采集。
2. 一级评论分页。
3. 二级回复。
4. 评论真实发布时间。
5. 原帖链接、标题、发布时间。
6. 导出字段与统一模型映射。
7. 增量采集去重。
8. 失败、登录过期和空结果状态。
9. 72 小时边界（71h、73h）验证。
10. 低频采集与平台规则检查。
