# 来源发现、追踪与增量采集

## 数据流

`comments` 中的 `author_key` 是当前来源发现的第一类信号。系统按平台和作者标识聚合已采集评论，并保留最多 10 条关联评论/内容证据。来源候选不是事实确认：它只表示某个作者标识在现有数据中出现过。

推荐分数采用可解释的启发式计算：

- 需求证据占 60%：已分析且分类不为“无效/其他”的评论比例。
- 内容量占 25%：关联评论数按 20 条封顶归一化。
- 活跃度占 15%：不同活跃日期按 7 天封顶归一化。

未运行需求分析时，需求证据项为 0；分数不能解释为作者质量或商业价值。候选保留证据、分数和理由，需人工审核后才能进入 `tracked_sources`。

## 追踪目标验证

- 当前自动发现只识别 `author_key`，不推导或伪造作者主页 URL。
- 来源审核通过后默认处于“未验证”状态。管理员必须填写平台实际接受的作者 ID / 主页目标，并显式标记 `tracking_verified=true`。
- 调度器只处理已启用、已验证、追踪范围为 creator，且平台登记了 creator 能力的来源。
- 当前 MediaCrawler 平台适配以仓库 `app/collectors/registry.py` 能力表为准；贴吧未登记 creator 能力，因此自动跳过。其他平台是否真实可用仍需授权账号本机实测。
- 不支持或未验证的平台会记录 skipped，不会把“链接可生成”误报为“可自动追踪”。

## 定时任务与执行批次

审核通过时自动建立来源计划。默认按来源配置的周期执行，允许暂停/恢复。后台调度器每 30 秒检查一次到期计划，每轮最多启动一个任务，按优先级排序；底层 MediaCrawler 仍保持单任务、并发数 1。采集启动失败或进程失败后，计划延后 15 分钟再试。运行批次保留 job ID、状态、起止时间、回扫窗口和失败原因。服务重启后，无法在当前进程任务表中找到的 running 批次会标记为 interrupted。

本地部署建议使用单个 Uvicorn worker。现有采集引擎的任务互斥仍是进程内锁，不适用于多 worker / 多实例同时调度。

## 增量游标与回扫边界

来源记录保存 `last_success_at`、`last_content_id` 和 `cursor_json`，可由连接器在成功采集后通过 checkpoint API 更新。存在平台游标时保存游标；没有游标时保存窗口起止时间，采用重叠回扫（默认保留 6 小时重叠，且不超过来源配置窗口）。

**当前限制：** MediaCrawler 命令行适配没有提供可靠的源端游标或发布时间过滤参数。因此调度器目前只记录建议回扫边界，不能声称平台端只返回该时间窗内内容；旧内容可能被重复扫描，且平台分页/排序变化仍可能造成遗漏。只有在具体平台适配器实现并验证游标/时间过滤后，才可将该平台标记为可靠增量。禁止通过提高请求频率规避平台限制。

## 幂等与采集时间

- 评论唯一键：`(platform, comment_id)`，重复导入更新字段，不增加重复评论行。
- 内容指纹：优先使用平台 + content_id；其次使用平台 + 去除 query/fragment 的规范化 URL；最后回退到平台 + 标题。
- 评论和内容均保留 `first_collected_at` / `last_collected_at`。首次采集时间不会因重复导入而覆盖。
- 标题回退指纹可能把同平台同标题内容合并；来源平台若提供稳定内容 ID，应优先使用。

## API

- `POST /api/v1/sources/discover`：生成/刷新来源候选。
- `GET /api/v1/sources/candidates`：按状态查询候选及证据。
- `POST /api/v1/sources/candidates/{id}/review`：通过、驳回或暂缓；通过时建立来源和计划。
- `GET /api/v1/sources`、`PATCH /api/v1/sources/{id}`：查询与配置追踪来源。
- `POST /api/v1/sources/merge`：将重复来源合并到目标来源（被合并项停用并留审计记录）。
- `GET /api/v1/sources/schedules`、`POST /api/v1/sources/{id}/schedule`：查看、暂停或恢复计划。
- `GET /api/v1/sources/runs`、`POST /api/v1/scheduler/tick`：查看批次或手动触发一次调度检查。
- `GET/PUT /api/v1/sources/{id}/checkpoint`：读取/保存增量检查点。

## 验证流程

1. 先在授权账号下完成平台采集和评论导入。
2. 运行需求分析以生成需求证据，然后执行来源发现。
3. 人工审核候选，确认来源类型、平台能力和实际追踪目标。
4. 将目标填入追踪来源并标记已验证，等待周期触发或手动调用 scheduler tick。
5. 检查来源运行记录、采集日志和导入结果；平台登录失效或权限拒绝时人工处理。
